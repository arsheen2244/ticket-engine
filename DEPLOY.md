# Deploying to the cloud (free tiers)

You deploy two services and two managed databases:

| Piece | Free option | What you copy from it |
|---|---|---|
| Backend (root `Dockerfile`) | Render (Blueprint in `render.yaml`) | public URL, e.g. `https://ticket-engine.onrender.com` |
| Frontend (`frontend/`) | Vercel (or Render, with `frontend/Dockerfile`) | public URL, e.g. `https://flashtix.vercel.app` |
| PostgreSQL | Neon or Supabase | host, db name, user, password |
| Redis | Upstash | `rediss://...` connection URL |

The browser only talks to the frontend. Next.js forwards `/api/*` to the backend, so the login cookie and the
live stock stream stay on one domain and no CORS setup is needed.

Kafka: free hosted Kafka is hard to find, so the cloud backend runs without `TICKET_ASYNC` and uses the
synchronous `redis` strategy. The web app handles both modes (`201` straight away, or `202` then polling).

## 1. Databases

1. Neon: create a project and copy the host, database, user and password.
   Neon shows `postgresql://user:pass@host/db`; the backend needs the JDBC form
   `jdbc:postgresql://<host>/<db>?sslmode=require`, with user and password in their own variables.
2. Upstash: create a Redis database and copy the `rediss://default:<password>@<host>:6379` URL.

## 2. Backend on Render

1. Push the repo to GitHub.
2. Render: **New > Blueprint**, pick the repo. Render reads `render.yaml` and creates the `ticket-engine`
   web service (Docker, free plan, health check `/actuator/health`).
3. Fill in the secrets it asks for:

| Variable | Value |
|---|---|
| `DB_URL` | `jdbc:postgresql://<host>/<dbname>?sslmode=require` |
| `DB_USER`, `DB_PASSWORD` | from Neon |
| `REDIS_URL` | `rediss://default:<password>@<host>:6379` from Upstash |
| `ADMIN_EMAIL` | the email you will log in with as admin |
| `ADMIN_PASSWORD` | a strong password (at least 8 characters) |
| `ADMIN_TOKEN` | optional; only used by the original benchmark API, which is off in this deployment |

   The Blueprint also sets these for you: `JWT_SECRET` (random, generated by Render),
   `COOKIE_SECURE=true` (login cookie over HTTPS only), `LEGACY_ENDPOINTS=false` (closes the original
   public benchmark API and its demo page) and `DB_POOL=5` (free Postgres tiers allow few connections).
4. Deploy. Flyway creates the tables on first start, and the admin account is created from
   `ADMIN_EMAIL`/`ADMIN_PASSWORD`. Check `https://<your-backend>.onrender.com/actuator/health` returns `UP`.

## 3. Frontend on Vercel

1. Vercel: **Add New > Project**, import the same repo.
2. **Root Directory:** `frontend`. The framework (Next.js) is detected automatically.
3. Environment variable: `BACKEND_URL` = `https://<your-backend>.onrender.com` (no trailing slash).
   It is read at **build** time, so redeploy after changing it.
4. Deploy and open the Vercel URL. Log in with the admin account and create a sale on **Admin**.

**Alternative: frontend on Render.** Add a second web service with Docker, root directory `frontend`,
Dockerfile `frontend/Dockerfile`, and build argument `BACKEND_URL=https://<your-backend>.onrender.com`.

## Secrets checklist

- Never commit `.env`; only `.env.example` (placeholders) is in git.
- `JWT_SECRET` must be at least 32 bytes and the same on every backend instance. Changing it logs everyone out.
- The frontend holds no secrets: `BACKEND_URL` is just an address.

## Cautions

- Free web services sleep when idle, so the first request can take about a minute. The frontend shows an
  error with **Try again** if the backend is still waking up.
- Some hosts buffer or cut long-lived responses. If the live count stream is interrupted, the event page
  reconnects, and after repeated failures it switches to polling every 3 seconds on its own.
- Benchmark with k6 against `localhost`, not a cloud URL; against the cloud you mostly measure your own internet.
